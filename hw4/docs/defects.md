# Разбор дефектов ДЗ 4

## 1. В лосс попадал промпт

**В чём был дефект.** Функция `mask_prompt` возвращала копию `input_ids` без
изменений. Поэтому модель получала обучающий сигнал на системной инструкции и
вопросе пользователя, хотя должна учиться предсказывать только ответ
ассистента.

**Как проявлялся.** Все позиции последовательности имели обычные метки, то
есть доля токенов в лоссе была равна 100%. Такая модель училась бы повторять
вопрос вместе с ответом.

**Как исправлен.** Граница промпта определяется в токенах. Все метки до неё
заменяются на `-100`, а токены ответа остаются без изменения. При несовпадении
токенов на границе используется запасной путь по символьным офсетам BPE.

**Числовая проверка.** В train сохранено 1 081 566 токенов, из них в лосс
попадает 444 727, или 41,1%. Проверка декодировала позиции `label != -100` во
всех 2197 сохранённых примерах и в каждом случае получила только ответ
ассистента.

## 2. Обучение и инференс использовали разные шаблоны

**В чём был дефект.** Текст для обучения собирался вручную из строк со
спецтокенами Qwen, а путь инференса использовал `apply_chat_template`. Это были
две независимые реализации одного формата.

**Как проявлялся.** Изменение шаблона токенизатора не попадало в обучающий
путь. Модель могла обучаться на последовательности, отличающейся от той,
которую она получит при генерации.

**Как исправлен.** Оба пути теперь вызывают `build_chat_text` из
`src/prompt.py`, а внутри него есть единственный вызов `apply_chat_template`.
Для инференса последняя реплика ассистента удаляется и добавляется generation
prompt; для обучения передаётся весь диалог. Ручные строки спецтокенов удалены.

**Числовая проверка.** Для всех 276 диалогов val строка инференса оказалась
побайтовым префиксом строки обучения. В каталоге `src` найден ровно один файл
с вызовом `apply_chat_template` и ноль вручную записанных спецтокенов ролей.

## 3. Использовался правый паддинг

**В чём был дефект.** В конфигурации был указан левый паддинг, но значение не
передавалось токенизатору, а `DynamicPaddingCollator` по умолчанию использовал
правую сторону.

**Как проявлялся.** В батче разной длины короткий decoder-only промпт
заканчивался pad-токенами. Генерация продолжалась после паддинга, поэтому при
`batch > 1` начало ответа могло быть испорчено.

**Как исправлен.** `tokenizer.padding_side` задаётся из `params.yaml`, а
коллатор по умолчанию паддит слева. Для pad-позиций `attention_mask` равна
нулю, а `labels` равны `-100`.

**Числовая проверка.** Значение `left` совпадает в трёх местах: параметрах,
`metrics/tokenize.json` и сохранённом `train.pt`. На контрольном батче из двух
примеров у короткой строки первая позиция attention mask равна 0, последняя —
1, а первая метка равна `-100`.

## 4. Обрезка не измерялась и была слишком большой

**В чём был дефект.** `truncation_stats` возвращала пустой словарь, поэтому
отчёт не содержал количества и доли обрезанных примеров. Исходный
`max_seq_len = 232` был взят для другого датасета и не соответствовал длинам
вопросов Ask Ubuntu.

**Как проявлялся.** После добавления метрики первый прогон показал обрезку
1806 из 2211 строк train, или 81,7%, и 229 из 276 строк val, или 83,0%.
Кроме того, у 904 train-примеров обрезка полностью удаляла ответ.

**Как исправлен.** Стадия считает `truncated` и `truncated_ratio` отдельно для
каждого сплита и печатает предупреждение при превышении порога 5%. По реальному
распределению длин выбран `max_seq_len = 1280`: p95 равен 1222 токенам для
train и 1135 для val, поэтому предел покрывает не менее 95% обоих сплитов.

**Числовая проверка.** После изменения обрезано 88 из 2211 строк train
(3,98%) и 10 из 276 строк val (3,62%). Обе доли ниже порога 5%; полностью без
обучаемых токенов осталось 14 train- и 3 val-примера, они исключены.
