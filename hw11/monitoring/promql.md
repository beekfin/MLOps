# Запросы для classic Histogram

TTFC p95 по Pod (секунды):

```promql
histogram_quantile(0.95, sum by (le,pod) (rate(hw11_ttfc_seconds_bucket[30s])))
```

TTFC p95 сервиса: сначала складываем bucket-счётчики всех Pod, затем вычисляем перцентиль.
Среднее перцентилей отдельных Pod не используется.

```promql
histogram_quantile(0.95, sum by (le) (rate(hw11_ttfc_seconds_bucket[30s])))
```

Полная длительность p95:

```promql
histogram_quantile(0.95, sum by (le,pod) (rate(hw11_response_seconds_bucket[30s])))
```

Для сравнения с клиентом каждый прогон B начинается и заканчивается паузой без запросов,
достаточной для двух сборов метрик. Сохраняем абсолютные `start` и `end`.
Копии не меняются между этими снимками. Воспроизводимый запрос конкретного прогона
записан в `results/prometheus/*-histogram-comparison.json`:

```promql
histogram_quantile(0.95,
  sum by (le) (hw11_ttfc_seconds_bucket @ END)
  - sum by (le) (hw11_ttfc_seconds_bucket @ START)
)
```

Гистограмма наблюдает TTFC только полностью завершённых ответов, как и клиентский p95.
Проверяем число успешных ответов по bucket `+Inf`. На клиенте использованы монотонные
часы; измерение дополнительно включает сеть и чтение фрагмента. Серверное распределение
оценивается линейной интерполяцией внутри границ bucket. Эти значения могут различаться.
Границы (с): 0.01, 0.025, 0.05, 0.1, 0.2, 0.4, 0.6, 0.8, 1, 1.5, 2, 3, 5, 8, 12, 20, 30, 60, +Inf.

В метках только Pod, версия и ограниченный набор исходов. Request ID и session ID
остаются в JSON-журнале, чтобы число временных рядов не росло с числом запросов.
