# ДЗ11. Kubernetes под нагрузкой

Продолжение `hw8910`. Разрешённый методичкой CPU-имитатор всегда возвращает
`backend_mode=simulated`. Kubernetes, HTTP, прогрев, очереди, мониторинг и нагрузка
настоящие; показатели не выдаются за скорость LLM. Обучение не запускается.

Условие — [source/homework11.html](source/homework11.html), связь с предыдущим кодом —
[source/continuation.json](source/continuation.json). Итог — [report.html](report.html).

## Запуск

Из корня репозитория перейдите в `hw11`. Нужны Linux x86-64, Docker, Python 3.12,
`uv`, доступ к интернету для первой загрузки, минимум 4 ГиБ доступной RAM и не менее
8 ГБ свободного места с запасом. До запуска проверьте `free -h`, `df -h` и
`docker info`. Начальные значения сохранены в `results/environment-before.json`.
Если Docker запрещает доступ к сокету, владелец компьютера выполняет
`sudo setfacl -m u:$(id -un):rw /var/run/docker.sock` в своём терминале.

```bash
cd hw11
python3 scripts/install_tools.py           # закреплённые CLI с проверкой SHA256
uv sync --frozen --group dev
make up                                  # собственный кластер kind с именем hw11
make check                               # локальные проверки и Helm lint
make check-k8s                           # 5 проверок, включая все опыты A
make experiment-b                        # 12 прогонов по 120 с + паузы и сбор данных
make experiment-c                        # HPA, горячий клиент, алерты
make report                              # 4 графика и HTML из полученных данных
```

Первый запуск скачивает образы. Опыт B занимает минимум 24 минуты измерений,
плюс паузы, завершение очередей и сохранение метрик. Он продолжает незавершённую
серию по сохранённым файлам, не подменяя пропущенные прогоны короткими.
Чтобы получить новую независимую серию, сначала сохраните прежние `results/`
под отдельным именем и запускайте с пустым каталогом результатов.
Во время опыта B не отправляйте посторонние запросы в API: они изменят сравнение
гистограммы и клиентских результатов. Опыты A, B и C запускаются последовательно.

Все команды используют `hw11/.runtime/kubeconfig`, не меняя пользовательский
kubeconfig. Параметры — `charts/hw11/values.yaml`. Точные ссылки реально установленных
образов — `source/installed-values.json` и `source/images-lock.json`; их передают Helm.
Образы мониторинга загружаются в узел через CRI по digest: это также обходит
ошибку импорта многоархитектурного index в сочетании Docker 29 / kind.

## Посмотреть стенд

```bash
export KUBECONFIG="$PWD/.runtime/kubeconfig"
.tools/kubectl -n hw11 get pods,svc,hpa,endpointslices
.tools/kubectl -n hw11 logs deployment/hw11-api --all-pods
.tools/kubectl -n hw11 port-forward svc/grafana 13000:3000
# В браузере: http://127.0.0.1:13000, панель «ДЗ11 — simulated CPU».
# В другом терминале:
.tools/kubectl -n hw11 port-forward svc/prometheus 19090:9090
```

Панель доступна локально в режиме просмотра. Настройки сбора каждой API-копии,
алерты и PromQL лежат в `monitoring/`. Исходная панель —
`monitoring/grafana/dashboard.json`, экспорт установленной панели через HTTP —
`monitoring/grafana/export.json`. Сервис приложения доступен клиентским Pod
по `http://hw11-normal:8000` и `http://hw11-sticky:8000`.

## Условия опытов

- Имитатор: одна обработка одновременно, очередь до 16, ожидание очереди до 45 с.
- Локальный LRU-кеш: 8 префиксов, hit=40 мс CPU, miss=160 мс CPU,
  вычисление фрагмента=3 мс CPU. В B: 4 фрагмента с паузой 0,09 с.
- Прогрев 20 с. Модель A/B берётся из immutable ConfigMap; SHA256 проверяется
  при загрузке. История диалога передаётся в запросе.
- По умолчанию 2 API-копии. CPU request=100m, limit=800m;
  память request=64Mi, limit=192Mi. Узел ограничен 4 CPU и 3 ГиБ RAM.
- B: четыре клиентских Pod с разными IP, новое соединение на запрос,
  4 запроса/с, 120 с, 480 запросов на прогон. Расписания совпадают между политиками;
  кеш перед каждым прогоном пуст, процессы прогреты. Три повтора каждой комбинации.
- C: HPA `autoscaling/v2`, CPU=60% от request, 2–3 копии,
  стабилизация уменьшения 45 с. Фактические времена — `results/c-summary.json`.
- Алёрты: p95 TTFC >0,5 с и отказы >10%; окно 30 с, минимум 10 наблюдений,
  условие удерживается 8 с. Сырые состояния сохраняются каждые 2 с.

В B обычный Service является также выбранным исправлением привязки ClientIP:
он проходит те же три повтора равномерного и горячего трафика. Внешний роутер,
SGLang и llm-d в обязательную часть не добавлялись.

## Где результаты

`results/requests.jsonl` — сводный журнал; `runs/` — каждая отдельная серия,
`schedules/` — плановые времена. `*-timeline.jsonl` содержит Ready, EndpointSlice
и HPA во времени. В `logs/` лежат серверные JSON-журналы, в `prometheus/` —
сырые ряды, bucket-счётчики и сравнение с клиентом. Request ID и session ID
хранятся в журнале, не используются как метки метрик.

`results/kubernetes-tests.log` — пять собственных проверок в Kubernetes.
`results/local-tests.log` — проверки хеша, кеша и входной схемы.
Четыре графика — `results/plots/`, подробные выводы — `report.html`.

## Размер и удаление

До запуска и после опытов сохраняются размеры образов, контейнера узла и каталога;
итоговая оценка — `results/footprint.json`. Для Prometheus задано хранение 2 часа
и 128 МБ; его временный том ограничен 256 МиБ, том Grafana — 128 МиБ,
каждого клиента — 32 МиБ. Данные измерений экспортируются в `results/` до удаления.
Мониторинг одноузлового учебного стенда использует временные тома, а не долговременное
хранилище. Файлы имитатора восстанавливаются из Helm ConfigMap.

```bash
make down                                # удаляет только kind-кластер hw11
# При необходимости удалить только собственные образы приложения:
docker images --format '{{.Repository}}:{{.Tag}}' hw11-service
# docker image rm hw11-service:<тег из source/installed-values.json>
```

Общие образы Python, Kubernetes и мониторинга могут использоваться другими
проектами: команда общего `docker system prune` не применяется. Локальные
окружения, CLI и kubeconfig исключены из Git. Для точного коммита сдачи:
`git log -1 --format=%H -- hw11` из корня репозитория.
