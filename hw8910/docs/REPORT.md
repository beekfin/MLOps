## 3. Процесс и сохранённая подготовка

`src/pipeline.py` связывает четыре задачи Prefect:
проверка входных данных → чтение/проверка готового артефакта → полный допуск →
публикация `accepted.json`. Между задачами передаются пути, ID и хеши,
а не модель или тензоры. Сервер Prefect локальный; его база в `.prefect/`.

Реальная стадия подготовки проверяет схему 50 вопросов: непустой текст,
уникальные ID и допустимые эталоны. Ключ использует SHA256 входных байтов,
ревизию и хеш токенизатора, шаблон, максимальную длину, версию и фактический
хеш кода подготовки. Путь и время изменения файла не заменяют содержимое.
JSON-результат хранится в workspace/cache; Prefect сохраняет описание в
workspace/prefect-results. Следующая задача действительно открывает
сохранённый результат. Для настоящего выпуска проверяется его связь с
golden-файлом и условиями токенизации. Изменённые данные не получают старый допуск.

Получение файлов по сети допускает максимум три попытки при временной
ошибке. Неверный JSON, несовместимость и отказ качества автоматически не
повторяются. В этом проекте один писатель и одна вычисляемая генерация.

## 4. Сбой, повтор и изменение входа

`make experiments` создаёт отдельные рабочие каталоги и новые процессы.
`flow-failed-after-prepare.log` показывает выполненную подготовку и
намеренный сбой следующей задачи с кодом 1. `flow-recovered.log` показывает
`Cached(type=COMPLETED)` и успешное продолжение с кодом 0. Ещё один повтор
не создаёт второго события. После изменения input.txt по тому же пути
`flow-changed-input.log` содержит PREPARED; после смены шаблона — также
PREPARED в `flow-changed-template.log`. Команды, коды завершения и отдельные
ID запусков сохранены в `process-experiments.json` и соответствующих логах.

Сбой после обновления указателя, но до записи события воспроизводится
`lab.py run --fail-after-pointer`. Сначала сохраняется намерение выпуска;
при повторе оно сверяется с принятым файлом и доводится до единственного
события. Журнал попыток — `attempts.jsonl`, события — `publications.jsonl`.
Источником согласования служит атомарно записанный `release-state.json`;
JSONL событий является восстанавливаемым представлением этого состояния.
ID выпуска включает модель, runtime и связанное решение оценки. Повтор с
другим runtime или другой оценкой не считается тем же выпуском.

Доказательства: `crash-after-pointer.log`, `recover-pointer-journal.log`,
`repeat-after-recovery.log`, `publication-recovery.json`. Файл указателя
записывается через временный файл, fsync и os.replace. Эта схема рассчитана
на одного писателя и не заявляет распределённую транзакцию нескольких серверов.

## 5. Допуск и сохранность принятой версии

`src.model_release.verify_evaluation` проверяет исходники протокола, ID,
параметры и хеши; заново считает метрики из сохранённых ответов и вызывает
неизменённую `quality_gate` ДЗ67. Результат переносится в
`metrics/release-report.json`. Вручную выставленного допуска здесь нет.
`validate_release` дополнительно проверяет полную схему, настоящий boolean
PASS, конечные метрики, соответствие модели и четырёх хешей.

Manifest закрепляет базу, адаптер и файлы весов/конфига, токенизатор,
шаблон, системную инструкцию, жадную генерацию, seed 42, лимит 32,
отключённое размышление, CPU/float32 и версии библиотек генерации из
исходной среды оценки. Хеши реальных файлов пересчитываются перед выпуском
и загрузкой. Полные исходные отчёты и ответы приложены в `metrics/hw67/`.

Неполный, чужой, отклонённый отчёт, NaN и ошибка os.replace не меняют
прежние байты accepted.json. Хеши до/после: `negative-publication.json`.
Синтетические отчёты STUB нужны для управления процессами; они не являются
оценкой Qwen. Полное настоящее решение отдельно связано с training/eval run.

Перепроверка дополнительно закрыла обход допуска через имя `fixture-`.
Тестовая модель теперь требует явного флага и текстового артефакта STUB ONLY.
Файлы настоящего адаптера сверяются с сохранёнными контрольными суммами
запуска обучения (`model-source.json`), а не только с заново вычисленными
хешами текущих файлов. Поэтому изменение dtype в описании артефакта не
наследует старую оценку. Настройки генерации сравниваются с сохранением
JSON-типов: число `0` не заменяет boolean `false`.
Опыты на временных копиях, показывающие отказ после исправления, сохранены
в `metrics/audit-binding-regressions.json`.

Уже принятый workspace не перезаписывается при подготовке другого
кандидата: для него нужен отдельный `--workspace`. Отказ подготовки
сохраняет не только accepted.json, но и каждый файл принятого адаптера.
Доказательство — `audit-prepare-preserves-accepted.json`; повторяемый
дополнительный опыт — `.venv/bin/python scripts/audit_bindings.py`.
Он читает отдельную копию артефакта и не загружает модель в память.

## 7. Настоящий API

FastAPI сообщает жизнь процесса через `/health`. До завершения загрузки и
прогрева `/ready` возвращает 503, затем 200. Успешный `/generate` содержит
текст, request_id, фактически загруженные model_id/runtime_sha256, выходные
токены и длительности. JSON запроса проверяется до генерации; произвольные
поля и неверные типы запрещены. Разрешён только закреплённый лимит 32,
вход до 8192 символов и 2048 токенов с системной инструкцией.

Реальный ответ: `{"answer":"A"}`,
выходных токенов 6.
ID: `my-qwen-adapter/1@0381294b884b46ea90076356c9e8db4f`.
Runtime SHA256: `279e20f7112eb90f9fe4bb330cf9dcf84b45c16cbfa3a631d6984f1decf47b3f`.
Ответ совпал с сохранённым ответом на тот же вопрос из оценки ДЗ67.
Это вопрос об urxvt: модель выбрала A при эталоне B — известная содержательная
ошибка кандидата сохранена. Успешный HTTP подтверждает работу интерфейса,
а не правильность каждого ответа модели.

Недопустимый лимит получил 422. Calls до/после: 1
и 1. Сохранённый успешный опыт перезапуска подтверждает повторную
загрузку той же версии и runtime. После исправлений отдельно успешно
загружен текущий manifest (`audit-real-api.json`). Доказательства:
`real-api.json`, `real-api-http.json`, `real-api-restart.json`, журналы сервера.

Первый пробный предел 3300 МиБ оказался мал: процесс остановлен ограничением
своей службы. Успешный запуск ограничен 3900 МиБ, без подкачки, с квотой
процессора 250%. После измерений служба остановлена. Предел сохраняется в
`make serve`; это инженерный запуск на CPU, а не замена dtype ради результата.

При дополнительном холодном старте во время перепроверки системе не хватило
свободной памяти, и процесс был остановлен OOM-механизмом. Это отдельная
попытка загрузки, не одна из 16 нагрузочных попыток; её журнал сохранён в
`audit-restart-resource-failure.log`. Успешные проверки настоящего API и
повторной загрузки сохранены отдельно. Теперь `make serve` сначала требует
не менее 5 ГиБ доступной RAM и при недостатке завершает запуск с понятной
ошибкой. Предел памяти службы является потолком, а не резервированием RAM.

## 9. Смена версии и откат

`scripts/demo_versions.py` (команда: `.venv/bin/python scripts/demo_versions.py`)
проводит отдельный **STUB ONLY** опыт. Сначала загружена A. Публикация B
не меняет ответ A до перезапуска. После перезапуска загружена B. Откат
принимает ранее проверенный manifest A; до перезапуска остаётся B, затем
снова отвечает A. Полная последовательность — `stub-versions.json`, HTTP
и серверные журналы. Это две лёгкие фикстуры, а не два обученных адаптера.

В реальном опыте одна принятая версия; отдельно доказана её загрузка после
перезапуска. Для следующего реального отката нужны сохранённые прежний
manifest, отчёт допуска, доступные файлы и совместимое окружение. После
публикации прежней согласованной комбинации надо перезапустить сервис,
дождаться `/ready` и сверить фактически загруженный ID.

## 10. Ограничения и связь с лекцией

Сначала модель обрабатывает весь вход (prefill), затем последовательно
добавляет токены ответа (decode). Сохранённые ключи и значения механизма
внимания — KV-cache — уменьшают повторные вычисления, но требуют памяти,
растущей с длиной контекста и количеством последовательностей. Простой
Transformers-сервис с блокировкой не реализует планировщик SGLang/vLLM;
его результаты не сравнивают скорость этих движков.

Ответ возвращается целиком, поэтому измерена полная задержка; время до
первого токена (TTFT) и интервалы между токенами (ITL) не измерялись.
Очередь не имеет отдельного ограничения длины; отмена HTTP-запроса не
обещает остановку вычисления. Это ограничения локальной учебной реализации.

Изучены методичка, 15 слайдов и полная 45-минутная запись; контрольные суммы
источников — `materials.json`. На решение непосредственно повлияли части
лекции 03:00–06:00 (малые описания между задачами), 09:00–12:00 (кеш и
восстановление), 12:00–15:00 (отказ по неполному отчёту), 21:00–24:00
(согласованный выпуск), 27:00–36:00 (готовность, генерация, очередь и
измерения), 39:00–42:00 (перезапуск и откат). Упрощённый loss-допуск
лекционного примера не заменял полное правило из ДЗ67.

Основные официальные справки: [Prefect: кеш](https://docs.prefect.io/v3/concepts/caching)
и [FastAPI: загрузка в lifespan](https://fastapi.tiangolo.com/advanced/events/).
